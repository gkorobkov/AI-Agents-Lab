# Разрыв соединения при долгом выполнении webhook

Проверено 9 ноября 2026 года.

## Наблюдения

- В браузере ответ потерян через 52 секунды. В n8n то же выполнение продолжалось больше минуты.
- `ui/index.html`: `CFG_REQUEST_TIMEOUT_MS` равен 5 минутам. Для webhook это предупреждение, а не вызов `AbortController.abort()`.
- `Part_2/Workflow_2.1_Tools.json`: Webhook использует `responseMode: responseNode`. Ответ отправляется через Respond to Webhook после AI Agent и парсера.
- Проверка `/healthz` вернула HTTP 200. OPTIONS для production webhook вернул HTTP 204 с разрешением POST, content-type и Origin сайта.
- В обоих ответах присутствует `server: envoy`. Это подтверждает наличие Envoy в маршруте, но не доказывает, что соединение закрыл именно он.

Установлено: клиентский таймаут не объясняет разрыв через 52 секунды. Точная причина требует Network-записи браузера и access/error-логов входного прокси за время ошибки. Успешный OPTIONS не гарантирует CORS-заголовки на ответе об ошибке от шлюза.

## Исправление на сервере

Для синхронного ответа нужно увеличить допустимое ожидание на **всех** промежуточных прокси до времени самого долгого workflow с запасом. В Envoy проверить route `timeout`, route `idle_timeout`, HTTP connection manager `stream_idle_timeout`, а также лимиты upstream и retry policy. `request_timeout` регулирует получение запроса от клиента и не заменяет timeout ожидания ответа.

Не включать автоматический повтор POST на прокси: workflow может продолжать выполнение после разрыва соединения, и повтор создаст ещё одно выполнение.

Для управляемого ingress Amvera передать поддержке домен, точное время запроса, длительность 52 секунды и ID execution n8n. Попросить проверить причину завершения запроса, response flags/details Envoy и увеличить лимиты ожидания ответа. Конфигурации ingress в этом репозитории нет; она здесь не изменена.

После изменения проверить отдельным диагностическим workflow ответ после задержки 90 секунд, затем после задержки дольше 5 минут. На фронте после 5 минут должна появиться возможность отправки нового сообщения, а первый ответ должен всё равно дойти. Не использовать основной агент для искусственной задержки.

## Вариант для выполнения без длительного HTTP-соединения

Если ограничения хостинга менять нельзя, требуется асинхронный серверный протокол: приём запроса и немедленный ответ с ID, сохранение статуса/результата в постоянном хранилище, отдельный endpoint чтения результата по ID. Фронт опрашивает именно этот endpoint, не отправляет исходный запрос повторно. Нужны авторизация чтения результата и защита от повторного выполнения по ID. Текущий workflow такого endpoint не имеет. Изменение только таймера фронта не добавит этот механизм.
