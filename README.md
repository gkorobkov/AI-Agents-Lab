# AI Agents Course Lab

Практический учебный проект для изучения AI-агентов: от первого запроса к LLM до агента с памятью, инструментами, RAG, наблюдаемостью и собственным пользовательским интерфейсом.

Главный элемент проекта — браузерная лаборатория в [`ui/`](ui/). В ней студент не просто общается с моделью, а видит весь цикл работы AI-приложения:

```text
параметр API → запрос → inference → ответ → наблюдаемый эффект → метрика
```

UI позволяет подключать n8n workflows через webhook, вызывать OpenAI-compatible API напрямую и работать со Stub-ответами без готового backend. Один интерфейс используется на протяжении всего курса: для API-экспериментов, отладки промптов, проверки памяти и tools, изучения RAG и анализа поведения готового агента.

## Чему учит проект

После прохождения модулей студент сможет:

- объяснить устройство LLM-запроса и ответа, а не только отправить prompt;
- управлять моделью через роли, контекст и параметры генерации;
- проектировать structured output и безопасно разбирать ответ агента;
- реализовать историю диалога и проверить её влияние на контекст;
- подключить внешние инструменты и задать правила их использования;
- построить RAG-контур с отдельными ingest и query workflow;
- диагностировать запросы по response, token usage, timing и debug-данным;
- тестировать узлы workflow и подготовить UI к публикации.

## Учебные модули

### 1. UI как лаборатория AI-агента

Студент начинает с [`ui/index.html`](ui/index.html) и исследует запрос через три транспорта:

| Режим | Для чего используется |
|---|---|
| **Webhook** | Подключение n8n, Make, Activepieces или собственного backend через GET/POST |
| **OpenAI API** | Прямой вызов `/v1/chat/completions` и эксперименты с параметрами модели |
| **Stub** | Проверка интерфейса, формата ответа, debug и задержек без модели и backend |

Интерфейс показывает текст ответа, источник, endpoint, безопасное представление request, полный response, время выполнения и token usage. Это превращает чат в диагностический стенд, на котором можно сопоставить изменение входного параметра с изменением результата.

В UI также реализованы:

- история и профили подключений;
- переключение PROD/TEST webhook и GET/POST;
- системный prompt, temperature и лимит output tokens;
- опциональная история OpenAI-диалога;
- копирование JSON и безопасного cURL без раскрытия API-ключа;
- единый debug-контракт `ai-agent-debug/v1`;
- suggestion-кнопки и форматирование ответа;
- RU/EN, светлая и тёмная темы, адаптивная desktop/mobile вёрстка;
- хранение API-ключа только в `sessionStorage`.

Пользовательская документация находится в [`ui/documentation.html`](ui/documentation.html), а локальный сценарий без backend — в [`ui/stub_json.json`](ui/stub_json.json).

### 2. OpenAI-compatible API и управляемые эксперименты

Лабораторная работа [`OpenAI API Lab.md`](OpenAI%20API%20Lab.md) подробно разбирает `POST /v1/chat/completions`. Для обучения этот endpoint удобен тем, что связь между request, поведением модели и response видна непосредственно.

Главная цель лабораторной:

> Понять, какой входной параметр чем управляет, где эффект проявляется в response и каким экспериментом это можно доказать.

Базовая программа состоит из 12 последовательных экспериментов:

| № | Эксперимент | Меняем | Наблюдаем |
|---:|---|---|---|
| 1 | Первый запрос | `messages` | `content`, `usage` |
| 2 | Выбор модели | `model` | модель, содержание, tokens |
| 3 | Контекст | `messages[]` | содержание, `prompt_tokens` |
| 4 | Случайность | `temperature` | вариативность ответа |
| 5 | Nucleus sampling | `top_p` | вариативность ответа |
| 6 | Ограничение длины | `max_completion_tokens` | `finish_reason`, tokens |
| 7 | Несколько вариантов | `n` | `choices[]` |
| 8 | Penalties | `frequency_penalty`, `presence_penalty` | повторяемость текста |
| 9 | Вероятности токенов | `logprobs`, `top_logprobs` | token probabilities |
| 10 | Structured Output | `response_format` | соответствие JSON Schema |
| 11 | Reasoning | `reasoning_effort`, `verbosity` | reasoning tokens, длина |
| 12 | Function Calling | `tools`, `tool_choice` | `tool_calls` |

Расширенная часть охватывает streaming, prompt caching, prediction, audio, moderation и web search. Следующий логический шаг — сравнение того же набора задач с `POST /v1/responses`.

> За один эксперимент изменяется только один независимый параметр.

Так студент может доказать причинно-следственную связь, а не просто получить другой ответ модели.

### 3. Structured output, парсинг и память

Материалы [`Part_1/`](Part_1/) вводят базовую архитектуру диалогового агента:

- системный prompt и строгий JSON-контракт ответа;
- разделение пользовательского ответа и диагностической информации;
- разбор output агента;
- получение `sessionId`;
- хранение и восстановление chat history.

Основные файлы: [`System_prompt_1.md`](Part_1/System_prompt_1.md), [`AI_Agent_Output_Parser.js`](Part_1/AI_Agent_Output_Parser.js), [`Get_sessionId.js`](Part_1/Get_sessionId.js) и [`JSON_Chat_Memory.js`](Part_1/JSON_Chat_Memory.js).

### 4. Tools, маршрутизация и контекст диалога

В [`Part_2/`](Part_2/) простой чат развивается в агента, который:

- определяет intent и выбирает нужную ветку обработки;
- учитывает предыдущие сообщения и уточняющие ответы;
- вызывает инструменты для погоды, событий, маршрутов и билетов;
- не подменяет отсутствующие данные выдуманными фактами;
- постепенно расширяется от одного инструмента до нескольких источников и RAG.

Версии системных промптов оставлены отдельно, чтобы сравнивать развитие инструкций и влияние правил на поведение агента. Готовые n8n-примеры находятся в [`Workflows/`](Workflows/): от погодного агента до City and Tickets Informer с наблюдаемостью.

### 5. RAG и база знаний

RAG-модуль показывает полный путь документа:

```text
документы → подготовка контекста → embeddings/vector store → retrieval → tool агента → ответ
```

В репозитории есть:

- [`RAG - Ingest Qdrant.json`](Workflows/RAG%20-%20Ingest%20Qdrant.json) для загрузки данных;
- [`RAG - Query Qdrant.json`](Workflows/RAG%20-%20Query%20Qdrant.json) для поиска;
- [`RAG KB Tool.json`](Workflows/RAG%20KB%20Tool.json) для подключения поиска к агенту;
- форматирование найденного контекста и unit-тесты;
- учебные документы в [`RAG/`](RAG/).

Модуль учит отделять знания модели от фактов базы знаний и задавать явные правила, когда агент обязан использовать retrieval.

### 6. Наблюдаемость, тестирование и эксплуатация

Финальная часть связывает workflow с инженерной практикой:

- полный request/response доступен для диагностики;
- backend debug отделён от пользовательского ответа;
- измеряются timing и token usage;
- JavaScript-узлы проверяются тестами в [`Workflows/`](Workflows/);
- webhook диагностируется через [`webhook-check.js`](webhook-check.js) и [`run-check.mjs`](run-check.mjs);
- UI собирается в `.build/ui/` и разворачивается существующими скриптами.

## Как работать с лабораторией

1. Запустите UI командой `ui-start.cmd`.
2. Откройте `http://localhost:8080/` и примите пользовательское соглашение.
3. Выберите Stub для знакомства без внешних сервисов, OpenAI API для экспериментов с LLM или Webhook для подключения n8n.
4. Включите Debug и зафиксируйте контрольный request/response.
5. Измените один параметр, повторите запрос и сравните результат.
6. Запишите наблюдение и вывод.

Для каждого эксперимента рекомендуется сдавать краткий отчёт:

```text
Эксперимент и изменяемый параметр
Контрольное и экспериментальное значения
Ожидаемый эффект
Request JSON
Response JSON
Изменившиеся поля response
Фактический результат и вывод
```

## Безопасность UI

- OpenAI API key хранится в `sessionStorage` и удаляется после завершения браузерной сессии.
- Ключ не попадает в профили, URL, preview, cURL, debug или console logs.
- Сохранённые настройки и webhook URLs находятся в `localStorage` браузера.
- Сообщения текущего чата существуют только в DOM и сбрасываются при перезагрузке.
- Прямой вызов API из браузера требует корректной настройки CORS у провайдера.

Используйте учебные или ограниченные ключи и не публикуйте секреты в workflow, примерах и commit history.

## Подключаемые материалы: лабы, Tools и MCP

У всех материалов один принцип: **один JSON-файл описывает один материал; манифест перечисляет файлы, которые сайт загружает в каталог**. Чтобы добавить материал, не нужно править JavaScript или создавать отдельную HTML-страницу.

| Материал | Манифест в `ui/` | Ключ списка | Готовый пример |
| --- | --- | --- | --- |
| Лабораторная | [`labs-manifest.json`](ui/labs-manifest.json) | `labs` | [`lab-chat-completions.json`](ui/lab-chat-completions.json) |
| HTTP-инструмент | [`tools-manifest.json`](ui/tools-manifest.json) | `tools` | [`tool-open-meteo-geocoding.json`](ui/tool-open-meteo-geocoding.json) |
| MCP | [`mcp-manifest.json`](ui/mcp-manifest.json) | `mcp` | [`mcp-student-example.json`](ui/mcp-student-example.json) |

### Добавление в общий каталог сайта

1. Скопируйте пример нужного типа в новый JSON-файл рядом с ним, в `ui/`.
2. Измените `id`, название и содержимое. Для отдельного материала нужен уникальный `id` внутри его каталога. Не добавляйте `builtin`: загрузчик сам отмечает материалы из манифеста как встроенные.
3. Добавьте имя файла в соответствующий манифест, сохранив существующие записи. Например:

   ```json
   {
     "schemaVersion": 1,
     "tools": ["tool-open-meteo-geocoding.json", "tool-my-search.json"]
   }
   ```

4. Запустите `ui-start.cmd`, откройте соответствующий раздел и проверьте материал. Страницы нужно открывать через HTTP, а не `file://`, поскольку каталог загружается через `fetch`.
5. Для публикации используйте обычный процесс сборки и деплоя. Загружаться должны и манифест, и перечисленные в нём JSON-файлы. Одна только запись в манифесте не создаёт файл.

Имена файлов: строчные латинские буквы, цифры и дефисы, расширение `.json`, например `tool-my-search.json`. В манифесте указывается только имя файла, без URL и подпапок. Пути разрешаются относительно манифеста. Лимиты общего загрузчика: 100 записей в манифесте, 2 000 000 байт на JSON, 15 секунд на HTTP-загрузку. Повреждённый или отсутствующий файл не блокирует остальные материалы: ошибка показывается в соответствующем разделе. При одинаковых `id` в манифесте используется первая успешно загруженная запись, а повтор отмечается ошибкой.

### Локальное подключение через интерфейс

В разделах «Лабы», Tools и MCP есть «Загрузить JSON». Выберите **файл материала**, а не манифест. После проверки он сохраняется в каталоге этого браузера и остаётся после перезагрузки. Это не публикация на сайте и не изменение файлов репозитория. Чтобы передать материал всем студентам, добавьте файл в манифест и опубликуйте сайт.

Tools и MCP можно скачать кнопкой «Скачать JSON» и использовать как основу нового материала. Для импорта отдельной копии задайте новый `id`: Tools и MCP отклоняют импорт с уже занятым `id`, не перезаписывая существующий материал. Лабы допускают повторное подключение того же определения; другой текст с тем же `id` отклоняется. Встроенная запись из манифеста имеет приоритет над локальной с тем же `id`.

Лабы также принимают JSON-отчёт с вложенным определением работы и восстанавливают ответы после подтверждения. Отчёты — отдельный формат, их не следует включать в манифест. Версия лабы (`version`) входит в ключ хранения отчёта: меняйте её при несовместимом изменении заданий.

### Содержимое JSON

**Лаба:** `schemaVersion: 1`, `id`, `version`, `title`, `description`, непустой `experiments`. У задания — уникальные `id`, `title` и `blocks`. Типы блоков: `paragraph`, `code`, `list`, `details`; пример всех полей находится в `lab-chat-completions.json`. Дополнительные разделы: `introduction`, `preparation`, `reportInstructions`. Для `id` лабы и задания используйте строчные буквы, цифры и дефисы.

**Tool:** `schemaVersion: 1`, `id`, `title`, `summary`, `docsUrl`, `providerUrl` и объект `tool`:

```json
{
  "schemaVersion": 1,
  "id": "my_search",
  "title": "Поиск города",
  "summary": "Возвращает координаты по названию города.",
  "docsUrl": "https://open-meteo.com/en/docs/geocoding-api",
  "providerUrl": "https://open-meteo.com/",
  "tool": {
    "name": "find_city",
    "description": "Найти координаты города по названию. Использовать перед запросом погоды.",
    "parameters": "{\"type\":\"object\",\"properties\":{\"name\":{\"type\":\"string\"}},\"required\":[\"name\"],\"additionalProperties\":false}",
    "strict": true,
    "http": {
      "url": "https://geocoding-api.open-meteo.com/v1/search",
      "method": "GET",
      "mappings": [{"key": "name", "value": "{{name}}"}],
      "body": "",
      "auth": {"placement": "none", "name": "", "prefix": "", "secretId": ""}
    }
  }
}
```

`parameters` — **строка с JSON Schema**, как в скачанном определении Tools; это не значения тестового вызова. `summary` предназначен для студента, `tool.description` — для модели. В `mappings` значение `{{name}}` берётся из аргументов вызова; обычная строка является константой. GET передаёт сопоставленные поля в URL, POST — в JSON-теле; непустой `body` задаёт свой JSON-шаблон тела. В `auth` задаётся только способ передачи ключа (`none`, `query`, `header`), имя параметра/заголовка, префикс и идентификатор слота `secretId`. Сам ключ вводится в UI, а не в публичный JSON.

**MCP:** `schemaVersion: 1`, `id`, `title`, техническое `name`, `description`, `mode`, `url`, `tools`. Для `mode: "workshop"` используется список инструментов с `name`, `description`, **объектом** `inputSchema` и `execution`. Обработчик `execution.type: "template"` возвращает JSON-шаблон из строки `template`; `execution.type: "http"` использует объект `http` такого же формата, как у Tools. Готовое определение учебного стенда находится в `mcp-student-example.json`.

Для подключения настоящего сервера используется тот же механизм файлов и манифеста:

```json
{
  "schemaVersion": 1,
  "id": "my_remote_mcp",
  "title": "Мой MCP-сервер",
  "name": "my-server",
  "description": "Инструменты курса на отдельном сервере.",
  "mode": "remote",
  "url": "http://127.0.0.1:3100/mcp",
  "tools": []
}
```

Замените `url` адресом своего сервера. Определение `remote` не запускает сервер: он должен уже работать и принимать Streamable HTTP, а браузер должен иметь доступ к его адресу. Список инструментов получается при проверке подключения. `workshop` выполняется локально в браузере и сам по себе не является опубликованным MCP-сервером. Токены вводятся отдельно в UI и не включаются в экспорт определения.

### Какие файлы за что отвечают

- `material-catalog.js` — общий загрузчик манифестов и JSON, ограничения путей/размеров, независимая обработка ошибок файлов.
- `labs.js` — проверка схемы лабы, задания и отчёты; `labs.html` подключает загрузчик перед ним.
- `tool-library.js` — каталог Tools, проверка определений и HTTP-вызовы; `tools-page.js` — редактор, импорт/экспорт и проверка; `tool-library-settings.js` — добавление инструмента к агенту.
- `mcp-library.js` — каталог и проверка MCP; `mcp-page.js` — редактор и импорт/экспорт; `mcp-runtime.js` — учебные обработчики; `mcp-client.js` — обмен с MCP; `mcp-settings.js` — подключение к агенту.
- В `index.html`, `tools.html` и `mcp.html` загрузчик подключается перед `tool-library.js`. Для MCP порядок: `material-catalog.js` → `tool-library.js` → `mcp-runtime.js` → `mcp-library.js` → `mcp-client.js` → код страницы/настроек. Каталоги Tools/MCP загружаются асинхронно: код, которому нужен готовый список, ждёт `ToolLibrary.ready` / `McpLibrary.ready` либо обновляется по событию `tool-library:change` / `mcp-library:change`.

Добавление JSON в каталог делает материал доступным для выбора, но не вызывает API и не подключает его автоматически к агенту. Для Tools/MCP студент отдельно нажимает «Подключить к агенту».


### Работа студента с HTTP-инструментом

Встроенные инструменты из манифеста доступны для просмотра. «Создать копию» находится вверху карточки. Пользовательские инструменты, включая ранее сохранённые копии и импортированные определения, остаются редактируемыми. При копировании имя функции получает суффикс `_copy`, затем `_copy_2` и далее; при сохранении проверяется уникальность имени в библиотеке.

Изменения сохраняются автоматически при потере фокуса или через 3 секунды без ввода. Над изменённым полем появляется «Сохранено». Если определение пока не проходит проверку, статус показывает причину и изменения остаются в редакторе; перед закрытием страницы завершите обязательные поля. Отдельной кнопки сохранения нет. Секреты по-прежнему задаются отдельно для текущей сессии.

Для освоения параметров доступны два пути:

1. **От HTTP к модели:** задайте имя параметра и «Постоянное значение», например `name = Москва`, затем выполните HTTP-проверку. Выберите «Создать аргумент»: редактор добавит аргумент в JSON Schema, сохранит Москву как тестовое значение и автоматически свяжет HTTP-параметр с аргументом модели.
2. **От модели к HTTP:** сначала добавьте аргумент в конструкторе раздела 3, затем выберите его в списке источников HTTP-параметра. Константы, например язык или число результатов, могут оставаться константами.

Вводить `{{name}}` вручную в параметрах не требуется: этот шаблон формируется внутри сохраняемого JSON. При переименовании аргумента его прямая связь с HTTP-параметром обновляется. Перед удалением используемого аргумента сначала измените источник параметра. Для GET тело запроса скрыто; для POST доступен JSON-шаблон.

После секции параметров запроса находится HTTP-проверка. Значения выбранных аргументов задаются обычными полями ввода; отдельный JSON аргументов не показывается. Группа переключателей перед значением: `txt` — «Задано вручную», значок робота — выбор аргумента, `+` — создание аргумента. Список аргументов оформлен внутри страницы и поддерживает клавиатуру.

После конструктора схемы находится «Проверка вызова LLM». Она использует текущие настройки модели, но выполняется отдельно от чата. Промпт автоматически собирается в форме «Вызови только инструмент … с параметрами …»; значения доступны для редактирования. В запрос отправляется ровно один инструмент и принудительный `tool_choice` с его именем. Ответ модели, включая `tool_calls` и фактические аргументы, показывается в этом же разделе. Проверка не выполняет HTTP-вызов автоматически и не добавляет сообщения в чат.

В readonly-превью определения инструмента отображается полный объект функции, включая `parameters` и `strict`. Предпросмотр API в настройках строится только из настроек: история чата, текст в поле сообщения и результаты незавершённых tool calls туда не попадают. Это правило относится также к копированию JSON/cURL из предпросмотра; реальные запросы чата по-прежнему используют контекст по его настройке.
